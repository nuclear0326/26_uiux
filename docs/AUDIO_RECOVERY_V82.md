# v82 초기 오디오 오류 분석 및 복구 검증

검증 날짜: 2026-11-25 (한국 시간)

## 확인한 원인과 확인하지 못한 부분

v81 초기 로그에는 IllegalArgumentException이라는 예외 종류만 남아 있어 장치 선택 단계인지 실제 열기 단계인지 구분할 수 없었습니다. 이번에 v81을 실제로 8회 다시 실행했으나 모두 정상 재생 상태였으므로, 당시 Windows 장치/드라이버 상태를 확정할 수 없습니다. 하드웨어 오류가 확실히 해결됐다고 주장하지 않습니다.

코드상 복구 결함은 확인했습니다. changeScene은 오디오 열기 성공 여부와 무관하게 currentScene을 먼저 기록하고, 같은 장면 요청은 바로 반환했습니다. 따라서 초기 BGM/빗소리 열기에 실패하면 같은 장면에 머무는 동안 자동 복구되지 않았습니다. 시작 음원도 한 번 실패하면 즉시 무음 연출로 전환했습니다.

기존 AudioSystem.getClip()은 실제 WAV 형식이 아니라 샘플링 속도 미지정, 16비트 스테레오 등의 기본 형식으로 라인을 요청합니다. 로컬 JDK 소스에서 확인했습니다. 이것이 과거 예외의 확정 원인은 아니지만 실제 음원 형식으로 라인을 요청하도록 바꿔 불필요한 형식 추정을 제거했습니다.

## 수정 내용

- AudioSystem.getLine(DataLine.Info)를 통해 원본 WAV의 실제 AudioFormat으로 Clip을 요청합니다. 음원 변환이나 리샘플링은 하지 않습니다.
- 초기 장면 음원과 미리 준비할 효과음이 실패하면 전용 오디오 작업자에서 150/400/1000/2000ms 간격으로 최대 4회 추가 시도합니다. 화면 스레드나 오디오 작업자를 sleep으로 막지 않습니다.
- 정상 재생 중인 BGM/빗소리는 그대로 두고 실패한 항목만 복구합니다. 같은 장면 재요청에도 트랙이 중복되지 않습니다.
- 장면이 바뀌거나 종료되면 이전 복구 작업을 취소합니다.
- 시작 효과음 준비 중에는 기존 UI 대기 상태(-2)를 유지합니다. 음원이 준비된 뒤 재생을 시작하고 원래 음원의 재생 위치로 화면을 진행합니다. 취소 시 늦게 재생하지 않습니다.
- 장치가 계속 불가능하면 제한 횟수 후 기존 무음 진행 방식으로 돌아갑니다. 재시도 횟수는 무제한이 아닙니다.
- 클릭음과 천둥 같은 일회성 효과는 실패 시 늦게 재시도하지 않습니다. 따라서 번개 이후에 밀린 천둥이 재생되는 변경은 없습니다.
- 실패 로그에 resource/decode/select-line/open-line 단계, 음원 형식, 예외 메시지를 남깁니다. timeescape.audioDiagnostics=true이면 상세 스택도 기록합니다.

## 실제 EXE 검증

테스트 전용 Java 에이전트로 실제 v82 EXE를 실행했습니다. 에이전트는 배포본에 들어가지 않습니다. 모든 저장 경로는 별도 테스트 폴더로 격리했습니다. 장치 상태는 오디오 작업자에서 조회해 데이터 경합을 피했습니다.

|---|---|---|
|1~10|정상 초기 실행|시작 효과음/천둥 Clip 열림, BGM/빗소리 2개 재생 및 위치 증가 확인|
|11~13|처음 4/8/12개 열기 요청 강제 실패|제한적 재시도로 실제 장치 Clip 복구, BGM/빗소리 2개만 재생|
|14|정상 시작 연출|실제 음원 시계, 균열 시점 통과, 연구실 진입 확인|
|15|처음 8개 열기 실패 후 시작 연출|준비 대기 후 재생, 균열 시점 통과, 연구실 진입 확인|

15회 모두 종료 코드 0. 정상 조건 로그에는 오디오 오류 없음. 실패 주입 조건은 의도적인 예외 외 실제 장치 열기 오류나 재시도 소진이 없었습니다. 연출 2회에서 화면 departure와 오디오 시계의 최대 표본 차이는 0.06초였습니다. UI 프레임 간격을 포함한 샘플 관찰이며 물리적 스피커 출력 지연의 측정은 아닙니다.

실패 주입은 장치 열기 단계의 소프트웨어 예외를 모사한 것으로 실제 USB 장치 제거/재연결 테스트는 아닙니다. 재생 상태와 재생 위치를 검증했으며, 사람이 음질을 청취하거나 스피커 출력을 녹음한 검증은 아닙니다. 모든 드라이버에서 무오류를 보장하지 않습니다.
